# Local ZK registry service (no rewards)

`scripts/zk_registry/service.py` adds a deterministic, closed-local service over the existing
[R/S/C package tools](zk-problem-registry.md). It builds a validated catalog, records commit–reveal
submissions, calls the existing production checks, updates lifecycle state, and independently replays
the same event log. Nothing is published automatically. No reward, signature, network, consensus,
bond, disclosure, upstream contact or activation path is implemented; BF.7 stays HOLD/default OFF.

## Catalog and public boundary

`catalog build` reads current ratchet waves, `correctness-cg1` and `spec-sg1` through their indexes.
Every admitted package passes `package.validate_problem` with actual file contents. The catalog excludes
private terminal states (DET-false, refuted/non-equivalent findings), FACT/structural-trivial properties,
noncanonical aliases, inactive requests and S inventory with missing authoring prerequisites.
Exclusions expose counts only. A direct package-directory input uses the same validation/filtering.

Each public entry includes id, R/S/C kind, framework, status, statement SHA256, R record or C specification
reference, and whether intake is available. R has no fixed Lean theorem until a candidate is compiled:
its public `Request.json` binds the immutable reference model and current record. Candidate-specific
equivalence theorem bytes and cost/admissibility are generated by the existing framework pipeline.
C publishes the exact `ProofStatement.lean`; S publishes its bound authorship request.

`export-public` writes a new separate directory with `catalog.json` and allowlisted request/model/spec
imports. It never exports the event log, object store, proof/candidate submissions, checker diagnostics,
private gate evidence, or a raw package directory. Export is explicit, local and no-overwrite.
Do not place a private store on a public file server: it contains submissions, salts and rejected inputs.

## Commit–reveal and ordering

A submission is a directory of regular files. Its digest binds a sorted manifest of relative names,
byte lengths and SHA256s. Symbolic links and escaped paths are rejected. Each file is limited to 16 MiB,
the complete submission to 64 MiB and the manifest to 1,000 files.

Commitment is SHA256 of canonical UTF-8 JSON with fields `domain`, `problem`, `solver`, `submission`,
`salt`, using domain `boole-zk-registry-commit/v1`. Canonical JSON sorts keys, uses compact separators,
and contains no NaN/Infinity. Solver identity is an opaque, bounded nonempty string, not a signature.
The store assigns a monotonic commit sequence under an exclusive filesystem lock.

Reveals must match the problem, solver, manifest and salt. A wrong binding is durably rejected without
consuming the intended commitment. A matched rejected proof consumes that commitment. The configurable
reveal interval is `[commit_time, commit_time + reveal_window)`: the exact deadline is expired.
Logical integer time is supplied explicitly (`--time`) or defaults to current UTC seconds; state never
reads the wall clock and time cannot move backwards. `advance` records time progression/expiry.

The earliest **valid commit**, not the first reveal, wins. A later valid reveal waits while an earlier
commit for that problem can still reveal. An invalid reveal or expiry releases that ordering barrier.
Once a winner exists, other valid reveals for the same property/rung are recorded as duplicates.
Unrevealed earlier commitments can therefore delay a result until their deadline. There is no identity
authentication, rate limiting, bond or Sybil defence in this MVP.

## Acceptance and lifecycle

- R: all six framework adapters call the existing final ratchet pipeline (`ratchet* .run_check` or
  `ratchet_native.run_check`). Admissibility, native compilation, strict cost order, generated equivalence
  statement and production proof/kernel checking are not reimplemented. PASS records the cheaper candidate,
  closes that rung and opens `<root-id>@<next-rung>` with the new record and unchanged reference semantics.
  Verdict provenance binds the pipeline's candidate source/R1CS and generated Lean-model digests; older
  frameworks' model digest is copied from the production-checked candidate import manifest.
  ZoKrates/halo2 initial records remain exactly bound to the reference cost/digest; later records must be
  strictly cheaper under the existing family order. Original model/source/IR bindings remain unchanged,
  and schema validation rejects unknown cost fields and inconsistent types. A zero-cost later record can
  be OPEN even when no further strictly cheaper candidate exists; this is not a promise of mining headroom.
- C: `correctness_gnark.check_solution` validates the package/environment and calls the unchanged production
  core on the exact package statement. PASS makes the property VERIFIED.
- S: current tracked tools validate historical D/M/C acceptance and request bindings, but do not provide a
  general new-spec differential/mutant/challenger rerunner. S stays listed but **not submittable**, with that
  reason recorded. The state machine's S pending-challenge/final states are reserved; historical
  ACCEPTED-LOCAL is not a newly completed public challenge window or an accepted service submission.

Rejected matches carry stable reasons (`invalid-proof`, `proof-failed`, `candidate-rejected` or
`checker-unavailable`) and private detailed reports. A supplied PASS label or alternate checker configuration
is never accepted as evidence. A checker error does not count as an accepted proof or as a discovered defect.

Production checks execute in a clean-environment worker with explicit local tool/environment configuration,
task-local scratch/cache paths, anonymous/config-disabled Git settings and no inherited credentials.
Lean is sequential and uses the existing owned-PID guard (PID plus stable birth time across exec), normally
12,000 MB and a single 1,800-second checker deadline. An explicit 20,000 MB setting is reserved for separately
resource-scheduled production finals; C retains its package's stricter limits. This is a cooperative sampled
guard, not an adversarial OS sandbox or certified exact peak-memory limit. Native source execution inherits
the existing framework pipelines' limitations. Do not accept untrusted parties on a network with this CLI.

## Event log and replay

`events.jsonl` is append-only, canonical JSONL. Each event binds its sequence, previous event hash, logical
time, type and payload. The hash is SHA256 of `boole-zk-registry-event/v1\0` followed by canonical event bytes
without the `hash` field. This is the local effect-0 receipt id; it causes no accounting effect.
Appends are flushed/fsynced. State is rebuilt from the complete verified log, not an authoritative state cache.
Incomplete tails, reordered/mutated events and missing/corrupt objects fail closed; no automatic repair removes
evidence. An exclusive lock serializes writers. Filesystem/power-loss guarantees remain those of the local host.

Package and submission bytes are immutable SHA256 objects, with manifests in the log. `replay` requires a new
empty destination, copies/verifies only referenced objects, revalidates the initial catalog, recomputes intake
binding and reruns **every matched verdict** with its own production checker. It must reproduce the event log
and final canonical state byte for byte. Verdicts cannot be trusted from hash chaining alone: a local owner can
rewrite/re-hash an unauthenticated log, and only independent rechecking detects a forged acceptance.
Latest-head/finality authentication, rollback detection against an independently held head, transport and
consensus are not built. A second node must independently provision the same pinned native snapshots/toolchains;
those large inputs are not silently replaced by the historical PASS records.

## CLI

Run with `PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=scripts python3 -m zk_registry.service`.
The store and output directories below are disposable local paths, not operator network state.

```sh
python3 -m zk_registry.service --store STORE catalog build --root PACKAGES --workspace WORKSPACE
python3 -m zk_registry.service --store STORE catalog list
python3 -m zk_registry.service --store STORE catalog show PROBLEM_ID
python3 -m zk_registry.service --store STORE --time 100 commit \
  --problem PROBLEM_ID --solver OPAQUE_ID --submission ANSWER_DIR --salt SALT
python3 -m zk_registry.service --store STORE --config CHECKER_CONFIG --time 101 reveal \
  --sequence 1 --problem PROBLEM_ID --solver OPAQUE_ID --submission ANSWER_DIR --salt SALT
python3 -m zk_registry.service --store STORE status
python3 -m zk_registry.service --store STORE --time 3700 advance
python3 -m zk_registry.service --store STORE --config CHECKER_CONFIG replay --out NEW_REPLICA
python3 -m zk_registry.service --store STORE export-public --out NEW_PUBLIC_DIR
```

`commit --commitment HEX` also records a precomputed commitment, without reading the answer or salt.
R answer directories contain `Solution.lean` plus `Candidate.circom`, `.nr`, `.go`, `.zok`, or a
`Candidate/` Rust overlay for AIR/halo2. C contains `Solution.lean`; imported copies, if supplied,
must still satisfy the existing checker integrity checks. Checker config binds `lean_env`, optional
`rss_mb`, framework `tools`, `snapshot_roots`/explicit `snapshots`, and task-local `build_root`.
Native AIR tool locations may be supplied explicitly through `native_path` and task-local
`native_environment` CARGO_HOME/RUSTUP_HOME; these are operator inputs, never solver-selected inputs.

Offline service/guard tests are registered in `scripts/self-test.sh`. The opt-in
`ZK_REGISTRY_SERVICE_LIVE_FIXTURES` JSON names existing private positive artifacts, checker config
and task-local output root for actual accepted R/C, sorry/changed-statement rejection and independent replay.
Such fixtures and their logs are never tracked or exported.
`catalog build` records the service's informational source digest separately from generator identities;
this is run provenance, not executable attestation or a replacement for independent checker replay.
