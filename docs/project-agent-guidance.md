# Boole 공통 에이전트 지침

## 적용 순서와 자율 진행

- 한국어로 결론부터 쉽게 보고한다. 필요한 전문용어는 뜻을 함께 설명한다.
- 사용자 요청과 기존 승인을 먼저 확인하고 실제 코드·현재 계획을 근거로 진행한다.
- 저장소 작업 절차의 상세 정본은 [개발 정책](development-throughput-and-evidence-policy-v1.md)이다. 과거 기록·스킬의 일반 절차가 새 승인 관문을 만들지 않는다.
- 사용자 지시가 정한 범위·금액·횟수·시간 제한을 유지한다. 이미 받은 승인을 같은 범위에서 다시 묻지 않는다.
- 현재 제품 상태와 다음 작업은 [현재 개발 위치](current-development-status.md)에서 시작한다. 기본 지침에 특정 실행 ID나 과거 단계의 금지 상태를 복제하지 않는다.
- “분석”, “검토”, “논의 후 결정”은 읽기·분석 요청이다. 구현·커밋·외부 변경으로 확대하지 않는다.
- “진행해”, “추천안으로 해”는 요청한 기능을 조사 → 구현 → 검증 → PR → CI → main 반영까지 완수하는 승인이다. 명시적으로 제외한 단계는 수행하지 않는다.
- “계속 진행”, “멈추지 말고 다음 작업”이면 현재 목표와 승인 범위 안의 후속 작업도 이어간다. 기능 완료, PR 병합, 일반 기술 선택은 자동 중단 사유가 아니다.
- 범위 안의 기술 선택은 추천안을 스스로 선택하고 이유를 알린다. 목표·외부 계약·보안 속성이 바뀌는 선택만 사용자에게 묻는다.
- 일반 compile/test/build 오류, 잘못된 경로·비교 기준·staging 배선은 정상 개발 과정으로 조사·수정한다.
- 새로운 비용·공개 배포·운영 자금/키·복구하기 어려운 삭제·보안/합의 약화 또는 기존 승인 상한 초과는 실행 전에 확인한다. 승인된 폐쇄 로컬 P2P 테스트와 공개 P2P 활성화를 구분한다.
- 위험한 결과를 분류하지 못했으면 해당 실행·채택만 보류하고 안전한 진단·수정 준비는 계속한다. 질문 전에 안전하게 준비할 수 있는 제안·증거·실행 범위를 구체화한다.

## 작업 단위와 검증

- 작업 단위는 사용자나 운영자가 확인할 수 있는 완결 기능이다. 보통 4–8시간 규모, branch 1개·PR 1개로 묶는다. 시간은 강제 대기나 목표 소진량이 아니다.
- 파일·함수·문서·지문 갱신마다 PR을 만들지 않는다. 관련 테스트·문서는 기능과 함께 반영한다.
- 동작 변경과 버그 수정은 의미 있는 RED → GREEN으로 검증한다. 이미 동작하는 기능은 회귀 테스트가 처음부터 통과할 수 있다. RED를 만들기 위해 제품을 일부러 망가뜨리지 않는다.
- 문서·설명·현재 커서 수정에는 새 실패 테스트를 의무화하지 않는다. 문장·날짜·파일명 복제보다 실제 동작·보안 경계·실행 배선 검사를 우선한다.
- 로컬에서는 변경의 직접 소비자 focused test만 실행한다. 전체 suite는 CI에 맡긴다.

| 변경 | 로컬 확인 | PR 확인 |
|---|---|---|
| 문서·작업 지침만 | docs-smoke, diff-check | 경량 process-only required checks |
| Python/셸·작업절차 검사 | 관련 테스트, 해당 언어 문법, diff-check | 분류기가 선택한 lane |
| Rust 테스트만 | 해당 focused test, fmt, diff-check | full CI |
| Rust 동작·의존성 | 직접 소비자 focused test, 관련 smoke, fmt, 변경 crate의 관련 clippy | full CI |
| 합의·격리·설치·공유 계약 | 위 항목 + 변경한 거절 경로의 소비자 테스트 | full CI와 관련 통합 gate |

- Rust가 바뀌지 않으면 cargo fmt/clippy를 관성적으로 돌리지 않는다. workspace clippy 2종과 full suite는 full CI가 강제한다.
- 이미 통과한 검사는 새 변경·실패·미해결 위험이 없으면 반복하지 않는다.
- 문서 전용 PR의 self-test/supply-chain/verdict-corpus 상태 이름은 유지하지만 Rust/Lean 설치·공급망 다운로드·이미지 재생산은 하지 않는다.
- CI 실행 분류는 scripts/ci_change_scope.py가 결정한다. 이름만 문서처럼 바꾸거나 허용목록을 넓혀 필요한 검사를 피하지 않는다.

## 스킬 적용

- 스킬은 필요한 작업 방법을 제공한다. 스킬의 계획 승인·인터페이스 확인은 사용자 요청과 기존 합의로 충족될 수 있다.
- 이미 승인된 범위에서 스킬 때문에 다시 승인받거나 별도 설정 인터뷰·문서 생성을 강제하지 않는다.
- 단순 오류에는 짧은 재현·수정을 사용하고, 어려운 버그에만 상세 진단 절차를 적용한다. 실행 재현이 불가능해도 로그·정적 증거 조사는 할 수 있으며 실행 검증과 구분해 보고한다.
- “테스트 하나씩”은 피드백 루프의 크기이지 PR·보고·승인 단위가 아니다.
- 공통 본문은 이 tracked 문서 하나로 관리한다. 로컬 AGENTS.md와 CLAUDE.md는 이 문서를 끝까지 읽는 진입점이며 승인·검증 규칙을 복제하지 않는다.
- 전역 스킬 파일은 프로젝트 수정의 일부로 임의 변경하지 않는다.

이 저장소에서 두 진입점은 gitignore 대상이다. 새 checkout이나 worktree에서 진입점이
없어도 이 tracked 문서를 직접 읽는다. 로컬 AGENTS.md와 CLAUDE.md에는 다음 진입점만 둔다.

```markdown
# Boole 프로젝트 작업 진입점

작업 전에 [공통 에이전트 지침](docs/project-agent-guidance.md)을 끝까지 읽고 적용한다.
상세 절차는 [개발 정책](docs/development-throughput-and-evidence-policy-v1.md),
현재 위치는 [현재 개발 위치](docs/current-development-status.md)를 따른다.

이 파일은 로컬 진입점이다. 공통 본문과 승인·검증·Git 규칙은 tracked 문서에서만 관리한다.
이미 받은 사용자 승인은 유지되며 스킬의 일반적인 확인 절차가 새 승인 관문을 만들지 않는다.
```

## 증거와 현재 문서

- 실제 실행·측정·사고·외부 결정과 consensus/release authority는 기존 증거를 보존한다.
- 계획·설계 초안·현재 커서는 제자리에서 고친다. 변경 이력은 Git이 보존한다. 과거 기록의 절차가 새 작업을 구속하지 않는다.
- 주요 기능 완료 시 현재 개발 위치와 Execution/Master의 current 절을 함께 갱신한다. 매 커밋의 일지를 여러 문서에 복제하지 않는다.
- tasks/lessons.md와 tasks/todo.md는 참고용 이력이다. 명시적으로 현 정책으로 채택되지 않은 교훈은 승인 규칙이 아니다.
- 동결된 배포/실험 세대는 그대로 보존하되, 개발 소스 수정까지 금지하는 것으로 확대하지 않는다. 필요한 후속 버전은 정상 변경·검증 절차로 만든다.

## Git과 사용자 파일

- 시작 시 status/diff를 확인하고 다른 작업의 변경은 보존한다. 필요하면 별도 worktree를 사용한다.
- 커밋 전 자기 변경의 diff/stat/diff-check와 예상 밖 파일을 확인한다. 사용자 변경을 clean 상태를 만들 목적으로 stash/reset/delete하지 않는다.
- author: NotoriAndo <281125350+NotoriAndo@users.noreply.github.com>. AI attribution/trailer는 넣지 않는다.
- codex/ feature branch → push → PR → 해당 required checks green → merge. main 직접 push와 보호 규칙 우회는 금지한다.
- 병합 후 원격 main과 동기화된 로컬 main의 SHA를 확인한다. squash 전 feature SHA와 main SHA가 같아야 한다고 요구하지 않는다.
- 자기 임시 파일·worktree는 종료 시 정리한다. 다른 세션 파일은 건드리지 않는다. Python 검사는 PYTHONDONTWRITEBYTECODE=1로 임시 캐시 누적을 피한다.
- 완료 상태는 “내 변경 정리 완료 + 기존 사용자 변경 보존”으로 보고할 수 있다.

## 모델·증명·운영 경계

- 유료 모델/API 실행은 기존 승인된 용도·예산·횟수 안에서만 한다. 승인 없는 신규 유료 호출은 하지 않는다.
- 실제 MCP/LLM 연결을 곧바로 특정 유료 API로 가정하지 않는다. 기존 연결·인증·비용 경로를 확인하고 선택된 경로를 승인 범위와 대조한다.
- public mining·benchmark·leaderboard 주장은 해당 실행과 근거가 있어야 한다. closed-local 결과를 공개망 성과로 승격하지 않는다.
- 답변 생성, ProofIntake 통과, verifier 통과, share/block/보상 반영을 구분한다. 모델이 답했다고 solved라 하지 않는다.
- 평가 프롬프트는 global contract → family manifest → official helper → output format → instance theorem 순서를 따른다. 문제별 비공개 힌트·정답 유출·모델별 우회는 금지한다.
- 운영 채굴·보상·합의·activation·지갑 자금 이동은 해당 범위의 명시적 승인이 있어야 한다.

## 보고

- 진행 중에는 발견·결정·남은 불확실성을 간결히 알린다. 변화 없는 CI 상태를 계속 나열하지 않는다.
- 완료 시 무엇이 동작하는지, 중요한 한계, commit/PR·push/merge, 관련 테스트/CI, 사용자 변경 보존 여부를 요약한다.
- 다음 작업은 승인 범위 안이면 이어간다. 의사결정이 필요한 경우만 추천안·이유·필요한 새 권한을 제시한다.
- wave 완료 시 유료 검증 구매자/LOI 수를 확인 가능한 값으로 병기한다. 이전 숫자를 확인 없이 최신값으로 단정하지 않는다.
